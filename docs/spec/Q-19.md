# 仕様: stop-gate の差し戻しカウントの書き込みを原子的にする

- 日付: 2026-07-25
- 関連 Issue / チケット: `docs/backlog.md` Q-19(起点は `docs/signals/S-8.md`)
- ステータス: approved

用語: **カウント** = `.claude/loop/stop-gate-pushback` に数値 1 行で持つ差し戻し回数。
**L1** = `scripts/project-checks.sh` の実行。**差し戻し** = フックが exit 2 で停止を止めること。

## 目的(なぜやるか)

`hooks/stop-gate.sh` はカウントが上限 3 に達したら L1 を打ち切る。赤が直らないまま
無限に差し戻すのを防ぐ歯止めは、これ 1 つしかない(stop-gate は goal.md を読まないため)。
そしてこの歯止めは、カウントが正しく読めることに全面的に依存している。読めなければ
`case '' | *[!0-9]*) count=0` で 0 に丸められ、上限に到達しなくなる。

書き込みは 3 箇所とも `printf ... >"$STATE"` の直書きで、これは「ファイルを空にする」と
「値を書く」の 2 段階になる。壊れる経路は 2 つある:

1. **書き込みが途中で失敗する**(ENOSPC・シグナル)。空のファイルが残り、次に書き込みが
   成功するまでカウントは 0 として読まれる。事前チェックの `: >>"$STATE"` は権限しか
   見ておらず容量を見ない(`docs/signals/S-8.md`)
2. **同じプロジェクトで Claude Code を複数開く**と Stop hook は並行して走り、
   一方が空にした瞬間に他方が読む

どちらも黙って歯止めが消える形の失敗で、ログにも残らない。

経路 2 について本項目が塞ぐのは**壊れた値を読むこと(torn read)だけ**である。
読んでから書くまでの間に他方が書く競合(lost update)は残り、そのぶん上限判定は
過小に数えられうる。これには排他ロックが要るため本項目のスコープ外とし、
`docs/signals/S-10.md` に射程を追記して引き取り手を作る。

## スコープ

### 含む

- カウントを更新する 3 経路 — 連鎖切れのリセット・赤での加算・緑での 0 書き戻し —
  を、一時ファイルへ書いてから置換する形にする
- **書き込みが成功したときだけ置換する**。失敗したら一時ファイルを消し、既存の値を残す。
  経路 1 が直るのはこの条件によるものであって、一時ファイルを経由すること自体ではない
- 書き込み可能性の事前判定を、実際の書き込み経路が成立するかどうかで行う。
  判定と実経路がずれると「書けると判定したのに書けない」が起きる
- 上記を検証する eval ケースの追加

### 含まない

- lost update(上記のとおり `docs/signals/S-10.md` へ)
- ENOSPC そのものの eval での再現。書き込み途中の失敗を注入する移植可能な手段が無い。
  検証は AC-3(一時ファイルを開けない場合)で代表させ、書き込みの成否を見てから
  置換していることはコードレビュー(L2)で確認する
- 書き込みに失敗したときの人間への通知。現行どおり黙って素通しする
  (`2>/dev/null` と終了ステータス無視を維持する)
- 一時ファイルが SIGKILL 等で残った場合の回収。次回の書き込みは別名を使うため
  動作には影響しない
- 置換後のファイルの mode。元ファイルの権限を引き継がず umask 由来になるが、
  内容は数値 1 行で機密性が無い
- `hooks/goal-gate.sh` と `scripts/loop-*.sh` の書き込み。goal.md はすでに一時ファイル
  経由の置換、台帳は追記のみで本問題を持たない
- 差し戻し上限の値(3)・リセット条件・検証の実行有無といった既存の判断の変更

### 副作用として受け入れるもの

**ディレクトリは書き込み可・カウントファイルだけ読み取り専用**という環境では、
従来素通ししていたラウンドで差し戻すようになる(事前判定が実経路に合うため)。
退行ではなく、判定を実経路に合わせた結果として意図した変化である。

## 設計上の決定(実装が従うこと)

- 置換は「一時ファイルへ書き、成功したら `mv` で被せる」形に限る。
  **置換先を unlink しない**。`rm` してから作り直す実装はファイルが存在しない窓が開き、
  読み手が `cat` に失敗して 0 に丸めるため、inode が変わっても原子的ではない
- 一時ファイルは `$STATE` と**同じディレクトリ**に置く。ディレクトリをまたぐと
  rename が原子的でなくなる
- 一時ファイル名にはプロセス固有の接尾辞を付ける。同時に存在するプロセス間で
  一意であればよい
- 書き込みに失敗した場合は一時ファイルを削除し、既存のカウントは変更しない
- 書けない環境では `stop_hook_active: false` でもリセットしない。カウントは空として
  扱い、上限判定を行わない(現行の `count=""` の扱いを維持する)。Q-7 が潰した
  「カウントの持ち越し」に見た目が似るが、上限判定そのものが飛ぶため実害は出ない

## 受け入れ条件

新規ケースは `evals/bin/hook-cases.sh` にシナリオを、`evals/cases/<id>.md` に
`type: command` / `expect_exit: 0` / `expect_output: ^OK:` のケースとして追加する。

- [ ] AC-1(`stop-gate-atomic-write`): カウント `1` を持つファイルが**存在する状態**から
      赤で 1 回差し戻したとき、(a) 内容が `2` になり、(b) inode 番号が更新前と異なる。
      直書きは同じ inode を上書きするため、inode の変化は置換で書かれたことの外形的証拠
      になる。ただし inode の変化だけでは unlink 方式を弾けないので、「設計上の決定」の
      1 番目に実装が従っていることを併せて確認する
- [ ] AC-2(`stop-gate-atomic-write` に同梱): 上記の更新後、`.claude/loop/` に
      `stop-gate-pushback.*` に一致するファイルが残らない。
      **これは退行ガードでありミューテーション対象外**(直書き実装では一時ファイルが
      そもそも存在せず自明に成立するため、AC-5 で落ちることを期待してはならない)
- [ ] AC-3(`stop-gate-readonly-dir-keeps-count`): カウント `1` を持つ mode 644 の
      ファイルが存在し、`.claude/loop` が `chmod 500` の状態で、`stop_hook_active: true`
      かつ L1 が赤になるフックを 1 回起動したとき、(a) 差し戻さず exit 0、
      (b) L1 を実行しない、(c) カウントが `1` のまま。
      現行実装は `: >>"$STATE"` が既存ファイルへの追記オープンに成功するため
      「書ける」と判定し、`>` での上書きもディレクトリの w を必要としないため
      成立してしまう。ゆえにこのケースは実装を変えない限り落ちる。
      **前提ガード**: このディレクトリに新規ファイルを作成できてしまう場合
      (root 実行で chmod が効かない場合)は判定せず ng で落とす。既存の
      `stop-gate-no-state-dir` のガード式 `: >>"$STATE"` はファイルが存在すると
      成功してしまうため流用できない
- [ ] AC-4: 既存ケースが通る — `stop-gate-red` / `stop-gate-green` / `stop-gate-clean` /
      `stop-gate-active-red` / `stop-gate-pushback-limit` / `stop-gate-pushback-reset` /
      `stop-gate-green-keeps-count` / `stop-gate-no-state-dir` /
      `goal-l1-runs-in-pushback-round` / `inner-loop-l1`。
      これらは stop-gate の書き込み経路を踏む既存ケースで、退行検出の主対象
- [ ] AC-5(ミューテーション確認): **変更前の実装**(`git show d5d8a10:hooks/stop-gate.sh`
      — 直書き + 事前判定 `: >>"$STATE"`)に差し替えると、`stop-gate-atomic-write` と
      `stop-gate-readonly-dir-keeps-count` の**両方が FAIL になる**。手順:
      1. 新実装をスクラッチパッドへ退避する
      2. `git show d5d8a10:hooks/stop-gate.sh >hooks/stop-gate.sh`
      3. `CLAUDE_PROJECT_DIR=$(pwd) ./scripts/eval-run.sh stop-gate-atomic-write stop-gate-readonly-dir-keeps-count`
         が FAIL 2 件で exit 1
      4. 退避した新実装を書き戻し、同じコマンドが PASS 2 件 / exit 0 になることを示す

      書き込み経路と事前判定は対で意味を持つ(片方だけ戻しても片方のケースしか落ちない)ため、
      ミューテーションはファイル単位で行う。コミット ID を固定するのは、auto-commit が
      ターン終了時に HEAD を進めるため `HEAD` 相対では再現できなくなるからである。
      報告には両ケースの FAIL 行と復帰後の結果を含める
- [ ] AC-6: `CLAUDE_PROJECT_DIR=$(pwd) ./scripts/eval-run.sh` が exit 0
      (不合格 0 件。claude CLI 不在による rubric ケースの SKIP は許容する)
- [ ] AC-7: `.claude-plugin/plugin.json` の `version` が `0.13.0` より上がっている。
      インストール済みのキャッシュはバージョン単位のディレクトリ
      (`~/.claude/plugins/cache/yuki-local/crystal/<version>/`)で、バンプしないと
      走行中のセッションは旧実装の `hooks/stop-gate.sh` を使い続ける。
      Q-23 はこれで撤廃が効いていなかった

## 制約

- 依存を増やさない。`flock` は macOS の base システムに無く、`mktemp` も使わない
  (`mktemp "$STATE.XXXXXX"` は BSD / GNU 双方で動くので移植性の問題ではなく、
  外部コマンドを 1 つ増やさないための判断)
- `hooks/` の変更はプラグイン更新後の全セッションに影響する(`LOOP.md`「2. 作業範囲」)。
  eval を通し、影響範囲を報告する
