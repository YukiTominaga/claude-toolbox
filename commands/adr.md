# /adr — ADR の作成と管理

「なぜこの構成にしたのか」「他にどんな選択肢があって、なぜそれを採らなかったのか」を
後から辿れるようにするため、決定を `docs/adr/NNNN-<slug>.md` に 1 決定 1 ファイルで記録する。
形式は `${CLAUDE_PLUGIN_ROOT}/templates/adr.md` を参照
(テンプレートはプラグイン側にしか無い。プロジェクト相対パスでは解決できない)。

`$ARGUMENTS` に応じて分岐すること。テーマ付き(`/crystal:adr 認証基盤の選定`)または
引数なしは `new` として扱う。

## `new`(既定) の場合

**4 フェーズを順に実行する。フェーズ 3 の合意を得るまでフェーズ 4 に進んではいけない。**

### 1. 情報収集 — 一次情報の所在を洗い出す

テーマを特定したうえで、このプロジェクトに残っている一次情報を集める。
存在するものだけを読み、無いものは無いと扱う(推測で埋めない):

| 情報源 | 何が得られるか |
|---|---|
| `.claude/decisions.md` | 決定した当時の生の記録。**最優先で読む**(読み方は下記) |
| `docs/spec/*.md` | 目的・スコープ・制約・受け入れ条件(`approved` / `done`) |
| `.claude/learnings.md` | ハマりポイントと非自明な発見(却下理由の根拠になる) |
| `git log` / `git show` | 実際に何がいつ入ったか。決定の前後関係 |
| 既存の `docs/adr/*.md` | 前提となる決定、および**文体・粒度の基準** |

テーマに直接関係する記述だけを拾う。関係の薄いものを混ぜると ADR がぼやける。

**`decisions.md` は全文ロードしない。** 追記のみで際限なく増えるファイルなので、
まずテーマの語で見出しを絞り込み(`grep -n '^## ' .claude/decisions.md` で一覧を見てから
該当エントリだけを読む)、`→ ADR-NNNN` のマーカーが付いたエントリは既に昇格済みとして
飛ばす。ファイルが 32KB を超えていたら、年ごとの分割
(`.claude/decisions/YYYY.md`)をユーザーに提案する。

### 2. 情報探索 — 実装で裏を取る

決定が実際にコードのどこに現れているかを読む。ドキュメントと実装が食い違う場合は、
**実装を事実として扱い、食い違い自体をユーザーに報告する**(どちらが正しいかは決めない)。

### 3. 内容確認 — 清書前の合意チェックポイント(必須)

**いきなり ADR 全文を書かないこと。** 方向性がずれたまま清書すると手戻りが大きい。
テンプレートの項目ごとに、箇条書きの骨子と根拠(どの一次情報から来たか)を提示し、
ユーザーの確認を求める:

- コンテキスト: 当時の制約・課題を 3〜5 行の骨子で
- 決定: 一行で断定した案
- 検討した選択肢: 採用案 + 却下案とその却下理由(**却下理由が ADR の主価値**)
- 影響: 得られるものと、受け入れるトレードオフ

このとき、**一次情報から裏が取れなかった項目は「材料なし」と明示する**。
特に却下理由は記録に残りにくく、最も捏造しやすい。埋められない項目は
ユーザーに直接質問するか、`<!-- 未確認 -->` として残す。もっともらしい理由を
書いて通すことが、この仕組みで唯一取り返しがつかない失敗になる。

### 4. 清書

合意が取れてから本文を書く。

1. 採番: `docs/adr/` 内の既存 ADR 番号の最大 + 1(4 桁ゼロ埋め)。ディレクトリが無ければ作成。
   採番前に `git fetch` して既定ブランチ側の ADR も見る(別ブランチで同じ番号が
   使われていても、手元のワーキングツリーだけでは気づけない)
2. ファイル名: `docs/adr/NNNN-<英小文字 kebab-case の slug>.md`
3. 既存 ADR があれば、その文体・見出し粒度・敬体/常体に合わせる。無ければテンプレートどおり
4. ステータスは既定 `accepted`(既に実装済みの決定を記録する場合)。
   これから決める提案なら `proposed`
5. 関連する既存 ADR があれば `関連:` に相互リンクを張る
6. 材料にした `.claude/decisions.md` のエントリ末尾に `→ ADR-NNNN` を追記する
   (エントリ本文は書き換えない。次回の情報収集でここを飛ばせるようにするための印)
7. **`"${CLAUDE_PLUGIN_ROOT}/scripts/adr-lint.sh"` を実行し、指摘ゼロにする。**
   必須セクションの欠落・番号の重複・プレースホルダの残留・却下案ゼロは
   ここで機械的に落ちる。指摘が出たら直してから次へ進む
8. パスと lint 結果を報告し、git commit をユーザーに提案する
   (ADR も `decisions.md` もチームの資産。両方まとめて 1 コミットにする)

## `list` の場合

1. `docs/adr/*.md` の番号 / タイトル / ステータス / 日付を一覧表示する。
   `superseded` は、どの ADR に置き換えられたかも併記する
2. `"${CLAUDE_PLUGIN_ROOT}/scripts/adr-lint.sh"` を実行し、結果を併せて報告する
   (ランナーはプラグイン側にしか無い。プロジェクト相対パスでは解決できない)。
   指摘があれば内容を示すにとどめ、**勝手に修正しない**

ディレクトリが無ければ「ADR は未作成。/crystal:adr <テーマ> で作成できる」と案内する。

## `supersede <番号>` の場合

決定を変えるときは、**既存の ADR を書き換えない**(なぜ変えたかが消えるため)。

1. 対象 ADR を読み、その決定と当時の前提を把握する
2. `new` の 4 フェーズで新しい ADR を作成する。コンテキストには
   **旧決定のどの前提が崩れたか**を必ず含める
3. 新 ADR の `関連:` に `ADR-<旧番号> を置き換える` を書く
4. 旧 ADR の `ステータス:` を `superseded by ADR-<新番号>` に書き換える
   (書き換えるのはこの 1 行だけ。本文には触れない)
5. `"${CLAUDE_PLUGIN_ROOT}/scripts/adr-lint.sh"` を実行する。3 と 4 は 2 ファイルに
   またがる編集で、片方だけ済んだ状態(参照先が無い / 逆リンクが無い)を作りやすい。
   lint はこの片側更新を検出する唯一の口なので、指摘ゼロを確認してから報告する

## 注意

- ADR にするのは**後から「なぜ」を問われる決定**だけ。ライブラリの単純な追加や
  命名の統一など、コードを読めば分かることは対象外
- 決定の記録であって設計書ではない。手順や API 仕様は `docs/spec/` に置く
- 機密情報(トークン、認証情報、内部 URL)を含めない
- 決定から時間が経つほど一次情報は薄れ、ADR の精度は落ちる。
  作れなかった項目は正直に空けたまま出し、後から補える形にしておく
