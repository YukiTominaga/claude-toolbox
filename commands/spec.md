description: 実装前に要件を定義し docs/spec/ に仕様を作成する
---
これから実装ではなく要件定義を行う。コードは一切書かないこと。

1. ここまでの会話とタスク内容から、目的・スコープ・受け入れ条件の草案を作る
   - **計画や設計メモを渡された場合**(plan mode の出力など、手段まで書かれているもの)は、
     次の対応で仕様に変換する:
     - 背景 / Context → 「目的」
     - 検証 / テスト方針 → 「受け入れ条件 AC-*」(検証可能な形でないものは 2. で質問して潰す)
     - **実装手段(再利用する関数・変更するファイル・章立て)は仕様に持ち込まない**。
       着手までにコードが変わると陳腐化し、古い手段を忠実に実装させてしまうため。
       手段は実装時点で決める
     - 計画に書かれていない範囲は「含まない」に**明示する**(計画は書いていないことを
       暗黙に除外しているだけで、境界を宣言してはいない)
2. 曖昧な点・複数の解釈がありうる点・スコープに含むか判断が必要な点を
   ユーザーに質問する。質問は一度にまとめて、優先度順に3〜5個まで
3. 回答を反映して `${CLAUDE_PLUGIN_ROOT}/templates/spec.md` の形式で
   docs/spec/<タスク名>.md を作成する(テンプレートを読んでから書くこと。
   同じ内容をこのファイルに複製しない — 二重管理は必ず片方だけ古くなる)
4. 受け入れ条件はすべて検証可能な形(実行できるコマンド・観測できる挙動)で書く
5. 仕様の規模が大きい場合は spec-critic サブエージェントで自己完結性を確認する
6. 仕様を提示し、ユーザーの承認を得るまで実装に着手しないこと

テンプレート: `${CLAUDE_PLUGIN_ROOT}/templates/spec.md`
(目的 / スコープ「含む・含まない」/ 受け入れ条件 AC-* / 制約 の構成)
