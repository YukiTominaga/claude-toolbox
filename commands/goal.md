# /goal — ゴール定義と自動達成判定

`.claude/goal.md` を管理する。このファイルが `status: active` の間、応答完了のたびに
goal-gate hook が Haiku で完了条件の達成を判定し、未達なら差し戻す。

`$ARGUMENTS` に応じて分岐すること:

## `status` の場合

`.claude/goal.md` を読み、以下を報告して終了する:

- frontmatter の status / round / max_rounds / cost_usd(judge の累積コスト)
- `## 完了条件` の一覧(チェック状態つき)
- `## 制約` の一覧
- `## 判定履歴` の直近エントリ(未達が繰り返されている場合はその旨も指摘する)

ファイルがなければ「アクティブなゴールはない」と報告する。

## `done` の場合

`.claude/goal.md` の `status:` を `done` に書き換える(通常は goal-gate が達成判定時に
自動で行うため、これは手動完了用の保険)。`.claude/goals/archive/YYYY-MM-DD-<slug>.md`
への移動を提案する。

## `abandon` の場合

`status:` を `abandoned` に書き換え、自動判定が停止したことを報告する。
`clear` / `stop` / `off` / `cancel` も同じ扱いとする。

## `resume` の場合

`status: stalled`(max_rounds に達して自動判定が停止した状態)のゴールを再開する。
同じ条件のまま再開すると同じ未達を繰り返すため、必ず見直しを挟むこと:

1. `## 判定履歴` と未達だった条件・制約違反を提示する
2. 見直しの前に、`crystal:verifier` サブエージェントで実態を確認することを提案する
   (judge は会話ログしか読めないため、「本当に未達なのか、検証コマンドの出力を
   出していなかっただけなのか」を実際のコード・テスト実行結果で切り分ける)
3. 確認結果をもとに、完了条件・制約の見直しをユーザーと行う
   (条件が過大だった / 検証コマンドが不適切だった / 制約が実態と合っていない、等)
4. 見直し後に `round: 0`、`status: active` に戻す
5. max_rounds を再確認する(前回で足りなかった根拠を踏まえて提案する)

`status` が `stalled` 以外の場合は、その状態を報告して何もしない。

## 引数なし、またはタスク説明の場合(ゴール新規作成)

1. `.claude/goal.md` が既に `status: active` で存在する場合は、その内容を提示し、
   上書きしてよいかユーザーに確認する
2. `docs/spec/*.md` を探し、`ステータス: approved` の仕様があれば取り込む。
   複数あればどれを使うかユーザーに選択させる:
   - `## 受け入れ条件` の AC-* → 完了条件 DC-* に変換する
   - `## 制約` と `## スコープ > 含まない` → goal の `## 制約` に取り込む
     (「含まない」はそのまま「〜しないこと」という制約になる)
   - frontmatter の `spec:` に取り込み元のパスを記録する
   - approved な仕様がない場合のみ、ここまでの会話とタスク内容から完了条件の草案を
     作り、ユーザーに確認する
3. 完了条件は DC ごとに検証コマンドを必ず併記する。判定器は会話に出力された内容しか
   読めないため、「観測可能な終了状態」と「それを証明するコマンド」をセットにすること。
   形式は templates/goal.md に従う:
   `` - [ ] DC-1: <観測可能な終了状態> — 検証: `<コマンド>` が <期待する結果> ``
   検証不能な条件(「きれいにする」等)はユーザーと具体化してから採用する
4. 実装系の DC には、対応するテストの DC を必ず立てる
   (例: `` - [ ] DC-3: DC-1 の挙動を覆うテストがある — 検証: `npm test` が exit 0 ``)。
   rules/testing.md の Exempt(ドキュメント・設定のみの変更、既存テストで担保される
   リファクタ)に当たる場合は、テストの DC を立てない理由を `## 制約` に明記する
5. `## 制約` を必ず確認する。spec から取り込めなかった場合はユーザーに聞き、
   制約がない場合も「なし」と明記する(空欄のままにしない。ゴールドリフト対策)
6. `max_rounds` を作業規模から提案し、ユーザーに確認する。固定値を提示せず、
   DC の数と作業規模を根拠に候補を出すこと(目安: バグ修正 3 / 機能追加 6〜8)。
   **8 を超える値は提案しない**: Claude Code は同一ターンの連続ブロック回数を
   既定 8 回で打ち切る(`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`)ため、9 以上にすると
   `status: stalled` にならないままランタイム側で強制終了し、
   `/crystal:goal resume` の導線に乗らなくなる。
   それ以上回したい場合は、この環境変数を上げる必要があることを伝える
7. テンプレート(templates/goal.md)の形式で `.claude/goal.md` を作成する。
   `round: 0`、`cost_usd: 0`、`status: active`、`created:` は今日の日付
8. `.claude/goal.md` が `.gitignore` に含まれていなければ追加を提案する
   (untracked のままだと stop-gate の「変更なし判定」を汚染するため)
9. ゴール定義の完了を簡潔に報告し、**応答を終えずにそのまま実装に着手する**。
   宣言だけで応答を終えると、その Stop で goal-gate が round=1 を消費し、
   「未達」の差し戻しという形で実装が始まってしまい、1 ラウンドを無駄にする。
   報告に含めるのは、完了条件・制約・max_rounds の要約と、
   「未達なら差し戻され、max_rounds に達すると status: stalled で停止する。
   停止したい場合は /crystal:goal abandon、再開は /crystal:goal resume」の一文まで
